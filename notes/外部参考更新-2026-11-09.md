## 二、★ 直接可用 / 需要我们现在就核对的条目（按价值排）
### 1) **工作组起始顺序决定 L2 复用**（上游 `6ef670e`，`src/gpu/gemm_staged.comp` 的 `STAGED_WALK_Y`）
**他们的实测**：**Intel 的 Windows 驱动按 Y 最快遍历一个 dispatch**（`work/tools-win/walk_order.py` 给每个工作组发号探针测出），Mesa 按 X 最快；后果 = 一个 row block 的 A 每个 column block 都要重读一遍（N=128 时 4 次）⇒ **短 K 的 GEMM 在 Windows 只有 Linux 一半速度**（Linux 80-88 GB/s，Windows 34-44 GB/s）。
**改法**：只改"哪个工作组算哪块"（`walk = gy + Ny*gx`，再拆回 row/col），**字节完全相同**（960 个输出四进程逐字节一致）。
**收益**：**网络快 9-19%**；staged GEMM 从 1.55-1.8× Linux 回到 1.2-1.3×；`58880x128x128 x4` 从 37.6-39.0 → 17.8-18.5 ms（Linux 16.3）。**⚠ 他们也记了反面**：**Window attention 在 walk 打开后反而多 0.5-2.5 ms ⇒ 必须逐核判定，不能全局翻。**
**我们这边的核对（已做）**：**我们引擎里 `nd_range<2/3>` 与 `range<2/3>` 出现次数 = 0（全是 1-D）** ⇒ 该改法对我们多半不适用；**且热点 f16 gemm 的分解已经是好顺序**：`gemm_f16_v1_kernel.hpp:65` `int tr = t / tc_n, tc = t % tc_n;` ⇒ **相邻工作组共享 row tile（A 复用）**。
**仍要做的**：**用他们的"发号探针"思路在我们口径下验一次 1-D 发射的真实起始顺序**（SYCL 1-D 是否真按 id 升序起组，我们从未直接验过）——**这是"帧语境溢价 1.3-2.1×"（§161/§169）唯一的现成解释候选之一**。
### 2) **一帧一次不可抢占的大 submit**（他们引 DLSSNR-AMD 原话）
> "A submit is not preemptible at any granularity that matters, so a 250 ms one blocks the compositor… The fix is not fewer dispatches… **It is more, shorter submits.**"
**我们的现状**：cgraph = **一帧一次提交**（44-59 ms 的设备块）；**他们当年据此解释"游戏里 GPU 占用只有 55%"**。
**这条可能正是用户实机上"帧数没按 bench 比例涨"的原因**（游戏自己的渲染要插进来）。**动作 = 在实机日志里看 NR 的 submit 是否压住游戏帧**（`out\nr_net.log` 已有帧时间；需要游戏侧 fps 对照）。
### 3) **pass 间 barrier 的宽掩码成本**（`01-references.md` + `notes/02-barrier.md`，RDNA4 实测）
相邻依赖 dispatch 之间完整 barrier ≈ **13 µs/个**；**完全去掉 = 一帧快 1.35×（barrier 合计 ≈ 26%）**；**宽掩码（`VK_ACCESS_SHADER_READ_BIT` 覆盖 sampled/uniform/storage）会连带失效 sampler/constant cache，而两个 pass 之间只动了 storage buffer ⇒ 精确化省下 0.67/9.2 ms = 7%**；`inv_barrier`（只保留 invalidate 半边）在 RDNA4 成立。
**他们已把开关落到代码**：`libxmx.c` 的 `barrier()` 宽掩码 + 新增 **`XMX_BARRIER_MODE` 0/1/2/3**。
**我们的核对**：**我们仓里没有 `XMX_BARRIER_MODE`**（层是工程师另一条线）；**我们的 C15 实测节点边界只值 ~2.2 µs/个** ⇒ 在我们这条 SYCL/L0-graph 路上 barrier 可能本来就便宜，**但"图边界的 cache-flush 成本"我们从未直接量过**（我们的 ladder 是"删节点"而不是"换 barrier 语义"）。**若要动，先做边界成本探针，再谈改。**
### 4) **ViT 自适应复用**（lmxxf `DLSS5_VIT_ADAPTIVE=1`）
**静止画面 +9~11%、运动画面 +5~6%**；他们当年的疑问原话：**"我们日志里已经有 held 85~87%，要确认复用粒度是不是同一个层级——如果我们的复用只在最终合成、而 ViT 每帧都重算，那这就是白送的 5~10%"**。
**我们的核对**：**我们仓里没有 `VIT_ADAPTIVE`/时间复用开关**（只有链跳 `NR_SKIP_CHAINS` 14/52，且用户已冻结为性能杠杆）；**我们的 ViT 瓶颈段每帧都在跑**（§168：8 条链 × 4 闭包 = 32 闭包 / 88 发，fused 腿 ≈ 20 ms/帧）。
**⇒ 这是剩下最大的"时间级"杠杆，但它改的是"每帧是否重算" = 画质域 ⇒ 必须用户裁决，不在我可自行 staged 的范围（军规 169①）。**
### 5) **数据类型扩面（int8/int4 mixed）**
lmxxf 的阶梯里最大一块 = **0.02+0.03 的数据类型改造（186 → 62 ms = −67%）**；DLSSNR-AMD 的 int4 = −11%；**A770 上 XMX int8 = fp16 的 2× 速率**。
**我们的现状**：**gemm 家族已经是 int8（dpas 8x8x32/Int32）**；**剩下 fp16 的是 attention/softmax 段**（fused 腿 `window_attention 13.6 + global_attention 3.61 = 17.2 ms`）⇒ 若要动，属改数值 ⇒ 同样要用户实机裁。
### 6) **SDPA 的实测分派契约与稳定性**（`refs/omni-xpu-kernel`，A770/DG2 真代码）
- **主机侧契约（v4.1 sidecar 实测）**：**`qLen ≤ 1024` 且 `qTilesFused * kvTilesFused ≤ 128` 才融合；否则 pack Q/K/V 一次 + 跑非融合 attention**；**`FUSED_RPT = 4`（融合几何）vs `RPT = 8`（非融合几何）**；**buffer cache 的 identity 必须含两侧 head 数，且淘汰不得释放异步核还在读的 USM**（`code-snippets.md:1903-1930`）；
- **online-softmax 稳定性（同一文件 1895 行前后）**：旧式 `exp2((m_old - m_new) * log2e)` 在 H3 尺度 score 跨度上**溢出成 inf/NaN 并产出黑帧**；稳定式 = `__ESIMD_NS::exp2<float, N>(...)` 且在 SxV 之前存 `p16 * rescaleCur`；他们做了 q/k ×10、v ×10 的压力测试无 65504 饱和；
- **执行模型常数（`api-usage.md:336-345`）**：**同队列两核提交为基线，双队列 + event 省约 17 µs/次**；**把 pack 融进 GEMM 反而每次亏约 47 µs**；**判断标准原话："只在额外设备时间小于它省下的启动间隙 + 主机开销时才融合"**；**graph 在 oneAPI 2026.1 不暴露逐节点 SYCL profiling 事件 ⇒ 节点时间要用 VTune `xpu-offload`**；**主机预处理若在计时循环里重复做：149 µs 的 GEMM 变 1311 µs（含 775 µs CPU + 301 µs USM 可见性）**。
**与我们的账对得上**：**17 µs 量级的边界成本 + "融合只在额外设备时间 < 省下的间隙时才划算"= 我们 C15（−0.63 ms / 290 只）、C20（删死提交只值 0.11 ms）、C22（折叠不过 20% 线）的外部印证 ⇒ 军规 186 的"减 submission 是弱杠杆"现在有第三方实测支撑。**
### 7) **A770 硬件常数与编译器陷阱**（`references/hardware/hardware.md`）
**L2 = 16 MB**（"A+B 工作集 2.5 MB 时完全 L2 常驻，预取无事可藏"——与军规 182 相互印证）；**L1 per Xe-core = 192 KB**；**DPAS `ExecutionSize=16` 头文件允许但 A770 上结果错（78/128 错），当不支持用**；**`dpasw` 只支持 ExecutionSize-8，16x16 tile 下指令数与 `dpas` 相同（不会更少）**；**`load_2d` / `prefetch_2d` 是 PVC-only，A770 上会挂；bf16 `Transposed` 编译期拒绝（只 u32/u64）**（与军规 172 一致）。

## 三、这次更新改变了什么结论
1. **军规 186 的"减 submission 是弱杠杆"现在有外部实测（17 µs 边界、融合亏 47 µs）与我们三铲（C15/C20/C22）互标 ⇒ 提高置信度。**
2. **新增一条我们从未验过的假设：1-D 发射的真实起始顺序与 L2 复用**（他们那边同类问题值 9-19%）⇒ **列为 B 案第一铲（W1）**。
3. **"时间级"杠杆（ViT 复用 / 短 submit 抢占性）在本项目里完全没做，且外部数字是 5-11% 量级** ⇒ **比第二层核内刀大一个数量级，但都属画质/架构域 ⇒ 必须用户裁决。**
4. **工具缺口明确：逐节点 GPU 时间要靠 VTune `xpu-offload`，本机没有** ⇒ 若要走 B 案（graph/放置级），**要么装 VTune，要么自己造 SYCL event/L0 计时探针（受"graph 不暴露逐节点事件"限制）**。

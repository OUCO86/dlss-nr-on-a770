### (2) ★ 但真根因不是 pinned/staging 配额 —— 是**一笔 4x 越界读**（仪器 bug，不是机器墙）
第一版改完仍失败，日志 `E:\DSH\s6\S1fix.log` 把它钉死了：

```
D2H faceB/faceA: bytes = Mp*C = 32640*64 = 2088960; scB/scT = Mp*4 = 130560
  [d2h scB] host-USM copy(522240 @0) threw code=1 -- chunked fallback
THREW at the STEP2 D2H: level_zero backend failed with error: 39 (UR_RESULT_ERROR_OUT_OF_DEVICE_MEMORY)
```
⇒ **faceB/faceA 那两笔 2,088,960B 的 D2H 完全成功**（走 host-USM 分块），死的是 **`scB` 的一笔 522,240B**。
算式：设备侧 `scB = mk(Mp*4)` = **Mp\*4 字节** = 130,560B（= Mp 个 float）；
host 侧当年写的是 `std::vector<float> hScB(Mp*4)` = Mp\*4 个 **float** = 522,240B，
拷贝长度取 `hScB.size()*4` = **522,240B ⇒ 请求 = 分配的 4.0x** ⇒ 越过 USM 分配尾端 ⇒
L0 把"越界读设备指针"报成 **OUT_OF_DEVICE_MEMORY(39)**。
**这就是 C2-6 那两行"失败点 free=1074MB/total=15932MB + 请求 2.09MB"的真相**：
数字都对，归因错了 —— 不是配额，是**尺寸单位 bug**（`*4` 在字节/元素之间串了位）。
修法（不改判据、不改数值）：`std::vector<float> hScB(Mp)` ⇒ 拷贝 `Mp*4` 字节 = 分配字节数 ✅。

## 第 1 步 ★ 整块 SLM 预算算术（先算再写码）
> ⚠ **本节的 (1)-(3) 三张表里的"别名后峰值"是手算的，加法错过（C=64/T=64 写成 65,824，真值 73,984）。
> 机器是对的：以 `E:\DSH\s6\s6b_layout.py` 的复算 + 第 2 步的实测为准，见本节末"第 1 步·修正版"。**

### (0) 记号与口径
- 链 = §16 实读的 **11 发**：`QUANT → BATCHED expand → QUANT → BATCHED proj → QUANT → GEMM_INT8_RESIDUAL
  → QUANT_WINDOW → QKV → WINDOW_ATTENTION → QUANT → GEMM_WINDOW_INT8_RESIDUAL`。
- **一个 WG 拥有一个 window 的全部 `TOK=64` token**（§16/§17 的 window 尺寸；S1 510 个窗、S2 128 个窗），
  或降到 **T=16 / T=32 token/WG**（一个窗被 4 / 2 个 WG 分摊）。
- 我们的网格 = **int8 + 每行 scale**（`pk` 面 1B/元素、`sc` 面 4B/token），中间激活面 f16 = 2B/元素。
  每 token 字节系数（与 §17 完全同尺，只是把 `sc` 的 4B 显式写出来）：
  `in/out/1267/1270/att = 2C`、`pk(C 宽) = C + 4`、`hidden = 8C`、`pk(hidden) = 4C + 4`、
  `qkv(3C) = 6C`、`scores = 2·TOK`（每 query 行 TOK 个 f16）。
- **B 权重 tile**：dpas 的 B 操作数在 SLM 里驻留（1a 的做法），取**最大单块** = expand `BK32×BN128×双缓冲 = 8192B`
  （proj/outproj/QKV 的 tile 4-6KB，相位串行 ⇒ 同一块别名复用）。
  另一档 = **B 不进 SLM**（R2 形态：global `block_load` 直喂寄存器）⇒ `BTILE=0`。

4. `1267`（f16，P6 写、P7 量化 + P11 skip 读）是**唯一横跨全 11 相的片**，**不可别名**：
   C=64 8KB / C=128 16KB —— 这块是"整块融合"的固定税。

## 第 3 步 ★ 三行判读
**① 整块 11 发在 C=64 档装不装得下？—— 全案装不下。**
别名后 **73,984B > 65,536B 帽，超 8,448B**，JIT 实测打死（cfg0 err 40）；
**C=128 更不可能**：T=64 全案 **139,520B = 2.13x 帽**（`hidden` 单片 65,536B 就吃满整顶帽）；
**T=16 全案 65,600B ⇒ 差 64 字节被拒**（cfg3）。
**唯一"不降 token 所有权"又进帽的形态 = 正好贴帽 65,536B**（cfg5 挪走 B tile + `sc` 落 global；cfg6 把 `pk2` 原位压紧），
此时 **驻留上界 = 1 WG/EU**；且 **BLKA（hidden ∪ qkv+att）单块 = 32,768B ⇒ T=64 档"回到 32KB 崖内"在算术上不可能**。

**② 11 个 barrier + 全片常驻的几何代价 = 栅栏几乎免费，全片常驻极贵。**
同布局只改栅栏数：cfg1 **11 栅栏 1.3512** / 1 栅栏 1.3419 / 0 栅栏 1.3455 ⇒ **11 个 `group_barrier` 只值 0.4-0.7%**；
cfg7 组 = **+1.8%**；cfg6 组 = 噪声内（11 个反而更快）⇒ **S6-1b 的失败不能记在栅栏头上**。
贵的是 **SLM 字节 ⇒ 驻留**：cfg8(16,384/驻4) **0.4750** → cfg7(24,640/驻2) **0.6457（+36%）** →
cfg1(36,928/驻1) **1.3512（+184%）**；C=128 同形：cfg10(32,768/驻2) 0.4690 → cfg9(41,024/驻1) 0.7526（**+60%**）
⇒ **跨 32KB 崖（驻留 2→1）在 stub 上就值 +60~+109%**（比 C1-9 在真链上量到的 +24.4% 更陡，因为 stub 的算术密度更低）。
**与 1a 的 0.4647 比（"纯几何吃掉多少"）**：
1a 的 6 发链 = GPU **0.3878** / wall **0.4510-0.4647**；
**最省的 11 相骨架（cfg8）= GPU 0.4750 / wall 0.5480 ⇒ 纯几何已经超过 1a 整条真链 +22%(GPU) / +18~21%(wall)，而它一次 dpas 都没做**；
按 1a 自己的所有权 T=32 做整块 = **1.1785-1.2000 = 1a 整链的 3.0-3.1x**；T=64 贴帽档 = **1.4490-1.5049 = 3.7-3.9x**。
⇒ **注意口径**：stub 替代的是"1a 的 6 发链 **+ 剩下 5 发**（QUANT_WINDOW / QKV / WINDOW_ATTENTION / QUANT / GEMM_WINDOW_INT8_RESIDUAL）"，
**后 5 发的现路单价本铲没测**（按令不扩范围），所以**这里只能给骨架价，不能给净收益**：
可说的硬事实是 —— **光是 11 相的驻留几何（不含任何矩阵数学）就已经 = 1a 整条真链的 1.22x（cfg8，最好档）到 3.9x（cfg5，贴帽档）**；
若把 cfg1（T=16 全案）当成"整块驻留"的代表，光骨架就比 1a 贵 **+0.96ms/链 × 20 链 = +19ms/帧串行** ⇒ **几何上直接死**。
⇒ **只有 cfg8/cfg10（16-33KB、驻留 2-4）这一档的骨架价（0.469-0.475）与 1a 同量级**，
而这一档**必然**把整窗 k/v 与 B tile 赶到 global —— 也就是把 §16 想消的往返重新付一遍。

**③ 若装不下：可行的切法 + 每种牺牲了 §16 里哪一笔收益**

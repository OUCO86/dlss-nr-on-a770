## 读表规则（诚实）

1. **上界不是结论**：只有组内真共享 weight 才成立。`_ffn_groups` 的 8 个 (N,K) 组是
   不同 block 实例（weight 不同）→ **不可沿 M 合并**（Mochi 的合并=一个窗口块一个
   megakernel，是沿 token 批不是跨 block 拼 weight）。真正候选=同 `record_qkv_projection`
   内不同 heads 的碎 M？需 nr_resident 探针确认 weight 身份。
2. **R8a 是硬门**：ΣM<8160 的组即使可合并也不该成为独立 int8 趟（§10 地板）——它们是
   megakernel 的 stage，红利在消 launch 不在拼 M。
3. 结论方向：跨 block 的 (N,K) 组基本不可拼（weight 不同）；可拼的只有**单 block 内**
   的窗口碎片（同 weight、同 N=3×channels、M=各窗口 token 数）。下一步=读 nr_resident
   确认哪些 site 循环内 weight 恒定、其 M 碎片能否沿窗口合并。

## ⚠ 上界已被证伪（2026-10-17 10:4x，读 nr_resident.py 坐实 weight 身份）

上表 10.98ms 是"假设组内共享 weight"的上界。读代码后**证伪**：

- `record_qkv_projection`（:428）调 `gemm_int8_qkv(s.aq, weight8, …, rows, …)`，
  `rows = windows * tokens`（:410 区）——**单个 block 内所有窗口的 token 早已在一次
  GEMM 里拼成大 M**。账本里同 (N,K) 的 8/4/3/2 趟 = **不同 block / 不同 level / 不同
  origin 的实例**，`w.qkv` 各自不同 ⇒ **不可沿 M 合并**。
- `_ffn_groups`（:771/:831）同理：每组 weight 不同（expand/branch/project 各层）。
- ⇒ **跨 block 的 (N,K) 组全部不可拼**，上界 10.98ms 塌回 ~0（对这些组）。

**真正的红利不在"拼 GEMM 的 M"**（block 内已拼），而在 §7⑥/§15 已定的两件事：
1. **消 elementwise 独立趟**（276 quantize + 120 residual + publish）折进 GEMM epilogue
   = 红利①——前辈已收割大半（残差折 epilogue 省 2.38ms 已进账本），剩 quantize 3.09ms
   的 P5 行-max 依赖只能靠"tile 拥有整行"消（§9/S 系列），不是靠拼 M。
2. **小 M block（l0=192/l1=2040）的整 level megakernel 化**（R8a：小 M 是 stage 不是
   dispatch）——消的是 launch 地板不是 M 宽度。

⇒ **v4=N=128 两半流式 fused-requant 的立项不受影响**（它服务 QKV 族 block 内已拼好的
大 M，真赢 2.3× vs 出货 fp16）；但"形状合并=沿 M 拼大 GEMM"这条**被离线表证伪**，
省下了一整条错误投资。合并的正确落点=elementwise 折 epilogue（红利①）+ 小 M megakernel
stage 化（R8a），**两者前辈都已部分做过，不是新方向**。

诚实记账：这刀的价值=**否证了一个诱人但假的 10.98ms 方向**，把重写路线钉回"消趟数靠
折叠不靠拼 M"。下一步不是写合并核，是接 v4（QKV 大 M fused-requant）——它才是已证真赢。

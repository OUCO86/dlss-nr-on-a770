## what to do with the 154 ms serial table
RUN_TIMING itself is ground truth (it waits per closure), so the 154 ms total is what the
frame really executes -- the corrections above apply to BENCH-DERIVED predictions, not to
the table. Concretely: the batched 18.5 ms row already contains the WIDE path (~2.15 ms
for these 20 sites), never the 7.17 ms split figure. Any knife priced off a dead branch
is worth zero, and the three-way check for a knife is now: (1) probe/arg-substitution that
the branch is reachable, (2) bench price, (3) frame A/B with the env set on ONE side only.
